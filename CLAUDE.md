# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

An Apple //e implemented in Verilog for the Sipeed Tang Nano 20K (Gowin GW2AR-LV18QN88C8/I7). The build uses the open-source toolchain (Yosys, nextpnr-gowin, gowin_pack, openFPGALoader). Video and audio go out over HDMI (720x480p with 48 kHz audio in data islands), audio also through the onboard MAX98357A I2S amp, and keyboard input plus a hardware debugger run over the 115200-baud UART on the BL616 USB-serial bridge.

## Commands

```sh
make            # full build: synth -> pnr -> pack => build/bitstream/Apple_TN20K.fs
make synth      # yosys only (build/yosys/top.json)
make pnr        # nextpnr-gowin (build/pnr/top.pnr.json)
make flash-sram # load bitstream into SRAM (volatile, fast; use for iteration)
make flash      # write bitstream to onboard flash (persistent)
make clean

make web-install   # npm install in web/
make web-build     # bundle web/dist, which the bridge serves
make bridge        # run the serial<->WebSocket bridge (scripts/bridge.sh)
make web-dev       # Vite dev server, proxies /ws to the bridge
make web-test      # node --test in web/
make web-charset   # build the glyph table from roms/apple2e_char.hex

scripts/build.sh [--synth|--pnr|--pack]  # the build itself; the Makefile wraps this
scripts/prog.sh [--flash]                 # openFPGALoader -b tangnano20k
scripts/bridge.sh [--port /dev/ttyUSB0]   # the web bridge; the Makefile wraps this
scripts/hdmi_diff.sh --check              # src/hdmi/ still matches its snapshot
scripts/hdmi_diff.sh --upstream           # what has TN20K-HDMI changed since
```

- **The Makefile has no build logic.** `scripts/build.sh` is the single implementation and the Makefile is a thin wrapper, so `make` and the OpenFPGA Deck produce the same netlist at the same paths. There used to be two flows with different nextpnr flags and different output paths; do not reintroduce flags anywhere else. Every stage re-runs from scratch, so iterate with `--synth`, then `--pnr`, then `--pack`.
- **New source files go in `sources:` in `fpga.yaml` only.** `scripts/sources.sh` reads that list, and `scripts/build.sh` (for `synth.ys`) and `sim/run.sh` (for `tb_top`) both use it. The Makefile has no `SRCS` list and `sim/run.sh` does not parse the Makefile any more.
- **`scripts/build.sh` gates on achieved Fmax**, not on nextpnr's exit status: it greps `Max frequency` out of `build/logs/pnr.log` and fails the build if the worst clock is below `VM_PIXEL_HZ` (27 MHz). It passes `--freq` but not `--sdc`, matching the Deck. `constraints/top.sdc` is the stricter alternative (it declares each clock domain explicitly, including the `clk_in` -> `clk_pixel` cross-domain path) if you want the fuller analysis; the log also reports a cross-domain path.
- `sim/run.sh` builds and runs all testbenches with iverilog (~80 s) and exits non-zero on failure; each testbench prints `PASS` or a line starting with `FAIL`, which `run.sh` greps for (Icarus ignores `$finish(1)`). `tb_video_hdmi` runs `video_generator` + `colorbar_gen` through `hdmi_tx` with `top.v`'s wiring and decodes every pixel from the TMDS lanes against an independent model of the text screen / bars (it catches a one-pixel look-ahead error). `tb_sound` checks the I2S frame rate and the 1 kHz test tone. `tb_input` drives the 115200-baud receiver with real bit timings and checks the host protocol end to end: legacy ASCII, the `FE` key packet with its paddle buttons, the `FF` gamepad packet, ANSI cursor keys, and `0x02` never reaching the keyboard. `tb_top` runs the whole `top.v` on `sim/models/gowin_prims.v` (behavioral `rPLL`/`CLKDIV`/`OSER10`/`TLVDS_OBUF`; Yosys' `cells_sim.v` has only empty shells for these, and no `CLKDIV`), checks the pins replay `hdmi_tx`'s symbols and that HDMI audio runs at 48 kHz; it needs the ROMs. `tb_video_hdmi` uses a *synthetic* char ROM (distinct data per address row), so it checks glyph *addressing*, not the real character set — nothing testbench-verifies `roms/apple2e_char.hex`'s contents, and the polarity and bit order of the real ROM are pinned instead by `web/test/charset.test.js`.
- The HDMI core `` `include``s `src/hdmi/hdmi_defs.vh` by repo-relative path, like the ROM paths, so run tools from the repo root.
- ROMs are gitignored (Apple copyright), so a fresh clone needs the user to supply them; see `roms/README.md`. ROMs are loaded with `$readmemh` using paths relative to the repo root (`roms/apple2e_rom.hex` is 16 KB covering $C000–$FFFF; `roms/apple2e_char.hex` is 4 KB, the 2732 — its size must match `apple2_char_rom`'s `mem[0:4095]`, since `char_rom_addr` is only 12 bits). Run tools from the repo root.
- **The character ROM is addressed with 6 bits of the character code**, not 7: `char_rom_addr = {1'b0, code[7]|(code[6]&flash), code[6]&code[7], code[5:0], glyph_row}`, so `$41` reads glyph 1 and bits 7/6 only select the alternate set. **A set bit in the ROM is a lit dot** (`pixel_on = glyph_byte[dot]`, no inversion; the `~` that used to be there made the text screen dot-inverted). Both halves of that are pinned by `web/test/charset.test.js`, which reads the same hex file; change one side and that test tells you.
- **The app talks to the board over Web Serial by default; the bridge is the fallback.** With the board plugged into the machine running the browser, `serial-link.js` opens the port directly and nothing needs installing — but only in Chrome/Edge, and only in a secure context (https or localhost), and only from a user gesture, which is why there is a Connect button. The WebSocket bridge in `web/bridge/bridge.mjs` exists for a board on *another* machine, for Firefox/Safari, and for the flash buttons (`openFPGALoader` needs a subprocess). Both satisfy the same small `Link` interface and both move raw bytes in both directions; only control messages are JSON. **The FT2232C has two channels and only one is the FPGA's UART** — they are indistinguishable in the device picker, so the choice is confirmed by asking the debugger (`02` then `?`, looking for the help line) and the wrong one is reported and closed. Keep that handshake; it is the only thing that tells the two apart.
- **Publishing the page.** GitHub Pages for this repo can only be served from a branch root or `/docs`, so `web/scripts/pages.mjs` builds the bundle, checks it, and copies it to `docs/`, which is the site's root (`https://terenceang.github.io/<repo>/`). **Everything in `docs/` is published**: the board documentation lives in `Documents/` precisely so it is not, and the script refuses to run if `docs/` holds anything it did not put there. Three things the check enforces: the published bundle must not contain the Apple 2732 (`charset.js` inlines `generated/charset.json`, and a Pages site is public the moment it is published, the same reason `roms/*.hex` is gitignored — `PAGES=1` in `vite.config.ts` aliases that import to `src/generated/no-charset.js`); asset paths must be relative, because a project site is served from `/<repo>/`; and no sourcemap. It exits non-zero and copies nothing if any of that fails; do not weaken it to a warning.
- **`web/src/keymap.js` is the Apple //e keymap and is tested as the era check** — `web/test/keymap.test.js` fails if a REPT key, function key, numpad, `⌘` or a Mac `*:` key appears, and asserts the reachable character set is exactly the //e's 40-column repertoire. Do not "fix" the keymap by adding keys without checking that test. The physical arrangement is data in `web/src/keyboard/layouts.js`.
- **`web/` is a separate Node project** and the only JS in the repo. It is a front end over the same UART, not part of the FPGA build: `make web-*` targets are the entry points, and `scripts/bridge.sh` is the only implementation of the Makefile's `bridge` target. Its logic is all testable from node with no browser, because Web Serial, WebSocket and localStorage are all injected rather than reached for globally. **If the bridge is used from a hosted page, it checks the `Origin` itself**, in `verifyClient`, because a WebSocket upgrade is not subject to CORS and the bridge can otherwise type into the //e, read its RAM and flash it for any page the user visits. Loopback and origin-less clients pass; anything else needs `WEB_ORIGIN`. Do not remove that check without replacing it with something that happens *before* the upgrade completes — closing with 1008 after the handshake still hands a stranger a live socket.
- The host protocol is documented in `web/README.md` and in the header of `src/input_controller.v`: `02` toggles the debugger and is dropped before the keyboard sees it; `FE <code> <btns>` is a keypress with the paddle button state; `FF 01 <btns> <x> <y>` is the gamepad; `1B 5B A|B|C|D` are the cursor keys; anything else is a plain ASCII keystroke. `<code>` is the **final** character, because a real //e's keyboard PROM (341-0132-D) resolves shift and caps lock before `$C000` and the ROMs take D6-D0 as final — so the app, not the RTL, owns the shift/caps logic, and `input_controller` stays a plain latch.

## Architecture

The design runs almost entirely in one clock domain. `clk_gen.v`'s rPLL turns the 27 MHz crystal into `clk_tmds` (135 MHz, 5× pixel clock), and `clk_pixel` is then derived from `clk_tmds` via a `CLKDIV` (divide-by-5) rather than tapped directly off the crystal — the HDMI `OSER10` serializers need a fixed, drift-free phase relationship between `clk_pixel` (PCLK) and `clk_tmds` (FCLK), which only a shared hardware divider off the same PLL output guarantees; feeding OSER10 two independently-routed clocks (frequency-locked but not phase-locked) causes the display to intermittently drop in and out of sync.

**Clock enables, not clocks.** `clk_gen.v` makes `ce_1m` (1.0227 MHz) and `ce_14m` from 32-bit phase accumulators. The 65C02 is clocked at 27 MHz but gated by `RDY = ce_1m & cpu_rdy`, and all softswitch and I/O logic is qualified by `ce_1m`. Keep new CPU-visible logic in this pattern.

**Shared RAM time multiplexing** (`apple2_core.v`): the 64 KB RAM is a single-port BRAM (`apple2_ram_64k` in `apple2_mem.v`). On cycles where `ce_1m=1`, the CPU (or the debugger) owns the address bus. On all other cycles the video generator's `vram_addr` is used, and `vram_data` is latched from those cycles. Video therefore sees RAM with a one-cycle registered latency, and `video_generator.v` prefetches the next column (`fetch_col`) to allow for this.

**Memory map / decode** (`apple2_core.v`): $0000–$BFFF main RAM; $C0xx I/O; $C100–$CFFF internal ROM; $D000–$FFFF language card (ROM or RAM, with the //e bank-switch semantics at $C080–$C08F). Aux memory, RAMRD/RAMWRT and 80-column display are *not* implemented. The 80STORE, 80COL and ALTCHAR flags are latched but have no effect on memory or video. `cpu_din` is a combinational mux: `input_controller` claims $C0xx reads through `io_hit`/`io_dout` (keyboard $C000/$C010, pushbuttons $C061–3, paddles $C064/5, $C070), and the core supplies $C011–$C01F status reads.

**Debugger path** (`serial_debugger.v`): pressing Ctrl+B (0x02) on the UART toggles `dbg_mode` and drops `cpu_rdy` to freeze the CPU. While paused, `effective_cpu_addr` switches to `dbg_mem_addr` so the debugger can read memory through the same `cpu_din` mux (`dbg_mem_din`). Commands are r/s/c/g/m/t/w/h/?/x plus `0 1 4 8 f v` to set the dump address; **they are only consumed when `main_state == M_IDLE`, and anything sent earlier is dropped without a word** — and the banner prints two prompts (one at the end of the banner string, one after the register dump), so a host that paces on the prompt will still lose commands. `web/` paces on 200 ms of silence instead. `w` (M_SCREEN) dumps the text page the video generator is showing plus the graphics page the bottom four lines use in mixed mode, and is only reachable while paused, which is what makes the read race-free — there is no spare bus to read $0400 while the CPU runs. In console mode the debugger echoes received bytes back, filtered to printable plus CR/LF/BS/BEL so the `FE` and `FF` packets do not land in the console as junk. `input_controller` owns the UART RX and passes `rx_byte`/`rx_valid` to the debugger; it drops keystrokes while `dbg_mode` is set. It also turns ANSI arrow-key escape sequences into Apple control codes.

**Video** (`video_generator.v`): the Apple 560×384 raster (192 lines doubled, 14 px per column) is centered at x=80..639, y=48..431 of the 720×480 frame, and `vbl` feeds $C019. The generator handles the Apple interleaved row addressing for text, lo-res and hi-res. It has no timing of its own: `hdmi_tx` owns the raster and samples `video_rgb` combinationally for its `(pixel_x, pixel_y)`, and because the generator's colour output is registered, `top.v` feeds it the *next* pixel (`h_cnt = pixel_x + 1`, `v_cnt = pixel_y`). `h_cnt` must step by one every clock (its column counter and RAM prefetch count clocks). Anything new that drives `hdmi_rgb` must honour the same same-cycle contract (`colorbar_gen` is combinational on `pixel_x`/`pixel_y`).

**HDMI** (`src/hdmi/`): a local copy of the HDMI transmitter from the TN20K-HDMI project (both are yours, both MIT), taken at commit `388b39e`. It is a copy rather than a submodule so this repo builds with nothing else checked out beside it, and it is not kept in step automatically — treat it as a snapshot, not a fork to merge. `scripts/hdmi_snapshot.sha256` records exactly what it is, and `scripts/hdmi_diff.sh --check` fails if any file is edited locally without re-baselining; `--upstream` shows what TN20K-HDMI has done since. The only deliberate local change is `hdmi_tx`'s `RGB_QUANT` parameter (see below); everything else is byte-identical. `~/TN20K-HDMI/CLAUDE.md` documents the internals in more depth than this file does.

`hdmi_tx` does CEA-861 720×480p59.94 (VIC 2) timing, the TMDS encoders (fixed 2-cycle latency in every mode, which the island scheduler's alignment depends on), and data islands carrying Audio Sample Packets, ACR (N=6144, CTS=27000), and the AVI and Audio InfoFrames. Mode and audio constants are in `hdmi_defs.vh`. The local `RGB_QUANT` parameter is the reason for the copy: `top.v` sets full range (`2'b10`) in the AVI InfoFrame because the Apple palette is 0–255, and a CE-mode sink would otherwise assume limited range and crush blacks. The `OSER10` + `TLVDS_OBUF` serializers are a generate loop in `top.v`; lane 3 is the TMDS clock (`0000011111`). `TLVDS_OBUF` is required on pins 33-40 (apicula rejects `ELVDS_OBUF` there with "it is a true lvds pin"), with `IO_TYPE=LVDS25` and one single-pin `IO_LOC` per leg in the `.cst`; the Tang Nano 9K's GW1NR-9 needs emulated LVDS instead, so don't copy that board's HDMI code here. The HDMI link has its own reset (`hdmi_rst_n`: PLL lock plus 128 pixel clocks), independent of `sys_reset`, so S2 resets the Apple without the display re-syncing.

History: an earlier HDMI-audio attempt using Sameer Puri's hdmi.sv packet library worked briefly, then reset the whole board once data-island activity ramped up (suspected power/timing margin in the much larger design). If the board resets or the link drops with this core, suspect that first. Holding S1 swaps only the picture (data islands and audio keep running), so it separates the Apple core from the HDMI link but not audio from video. Diagnose with a scope/logic analyzer rather than blind hardware iteration.

**HDMI bring-up test pattern** (`colorbar_gen.v`): holding `btn_s1` (active-high, pulled down by board 1k resistor) forces `top.v`'s HDMI mux to an 8-bar color pattern with a border and a blinking liveness box, independent of the CPU/RAM/`video_generator`, plus a 1kHz test tone (`sound_generator.v`'s `test_tone_enable`) on the I2S speaker and HDMI audio — use this to isolate the clocking/serializer/display chain from the rest of the design when video misbehaves.

**Audio** (`sound_generator.v`): any access to $C03x pulses `spkr_pulse`, which toggles the speaker flip-flop. That drives a damped-impulse sample model sent out over I2S. `audio_sample` updates once per 64-BCLK frame, and the frame rate is **exactly 46.875 kHz** because 27 MHz / 46.875 kHz is exactly 576 clocks and 576/64 = 9 clocks per BCLK. 9 is odd, so `bclk_div` free-runs 0..8 and toggles BCLK at both 4 and 8 (4 high, 5 low). A single toggle compare gives an even period, lands on 42187.5 Hz, and puts the 1 kHz test tone out at ~900 Hz. The same sample is resampled at 48 kHz by a fractional accumulator in `top.v` and sent over HDMI as stereo L-PCM, so the two rates are coupled: change one and you must change the other. `sim/tb_sound.v` checks the BCLK period, the frame interval and the tone frequency. `test_tone_enable` (wired to `btn_s1` in `top.v`) substitutes a 1kHz square wave for bring-up testing.

**Block RAM is the scarce resource, not LUTs.** This device has 46 BSRAM and the design uses 42 of them (64 KB RAM = 32, system ROM = 8, char ROM = 2, plus small ones), against 6780/20736 LUT4 and a `clk_pixel` Fmax of ~70 MHz against a 27 MHz target. Adding a memory means finding BSRAM first; logic is nearly free. The char ROM is 4 KB rather than 8 KB precisely to keep two BSRAM blocks free, and `char_rom_addr` is only 12 bits.

**CPU** (`src/cpu/`): Arlet Ottens' 6502 core with the 65C02 extensions by David Banks and Ed Spittles. It has been modified to expose `debug_*` register ports. IRQ and NMI are tied low.

## Hardware notes

- The pin assignments live in `constraints/top.cst`. The Tang Nano 20K LEDs are active-low. Their mapping is listed at the bottom of `top.v`: heartbeat, PLL lock, reset, CPU write, text mode and key strobe.
- `btn_s1` (active-high, pulled down) holds the HDMI/audio output on the color-bar test pattern (see above). `btn_s2` (active-high, pulled down) triggers a clean manual reset. Automatic reset also runs via the power-on counter in `top.v`.
